# 无限时长与评分建议

状态更新：2026-09-19，后续独立迭代已实现无限时长、累计用时、取消医疗时间催促及闲置采样保护，见[无限时长试玩版](../implementation/无限时长试玩版.md)。下文保留最初的设计依据和调整前问题清单；数值评分、效率奖励、收起时钟及跨服务续玩仍是建议，尚未实现。

## 推荐第一版

采用 **无限任务时长 + 累计用时 + 原有行动耗时**。移除十分钟强制结束，允许花二十分钟、一小时或更久完成同一局；持续时间本身不能使任务失败。当前运行库与正式部署的保存/恢复能力仍需分别验证，不能把“没有时间上限”宣称成“随时关闭服务都能继续”。

| 玩家体验 | 建议行为 |
| --- | --- |
| 看地图、阅读卡片、与顾问交流 | 可以持续探索，不会因达到总时限结束，也不因阅读慢丢失线索 |
| 时间显示 | 显示中性“已用时 12:35”，可以收起；移除剩余时间、临近截止变红和催促文案 |
| 调查、等待、路线执行 | 保留原有行动时长、并行调查、资源成本和实时车辆运动 |
| 任务结束 | 完成抵达/交接规则，或玩家主动结束；不再由累计时间触发失败 |
| 医疗叙事 | 保留需要转送的背景，取消现实八分钟触发的催促；将转送是否完成作为任务结果描述 |
| 复盘 | 展示完成情况、实际用时、调查与路线成本，以及现有行为分析 |

保留调查额度、来源独立性、路线代价和信息不确定性，决策仍有取舍。只移除时间压力，无需同时放开所有资源或让每次调查都免费。

## 用时如何参与评分

**建议初版先记录、先展示，不直接扣基础分。** 试玩几轮得到合理的时长分布后，再增加少量效率奖励，上限建议先试基础分的 5%，而不是使用每分钟持续扣分。

- 完成任务及交接、证据核验、决策依据和资源使用应是主要评价内容；快不能抵消遗漏重要手续或缺乏依据的决定。
- 效率奖励只在任务完成、必要条件满足后计算。超过参考用时不终止游戏，也不把基础成绩扣到负值。
- 游戏计时可记录总经历时长；用于效率评价的时间需要另行定义，明确扣除技术故障、强制系统等待和明确暂停。并行等待区间必须按时间区间合并，不能多次扣除。
- 等待 AI 回答不应让使用较慢模型的玩家吃亏。调查和行驶是玩家选择带来的任务成本，需要与技术等待区别处理。
- 在有暂停/恢复、活跃时长定义和参考数据之前，先不上排行榜。否则阅读速度、手势调试、离开电脑和网络性能会影响所谓的“能力分”。

现有 AI 复盘的四维是行为观察：核验不足、缺乏依据的拒绝、低增益检查的成本，以及基于证据调整判断。它们没有统一数值总分，也不相加为 100%。若要新增游戏分数，应由后端根据可核验事实和版本化规则计算，与 AI 的文字解释分开；不要把“读得久”直接当成过度谨慎。

## 为什么暂不直接拆成回合制

当前卡片 `validUntilMissionMs` 全为 `null`，报告标签不会随阅读时间动态变更；任务入口主要由场景、资源、岗位占用和上报额度决定。没有“玩家思考几分钟，证人就自动离开”的机制。因此取消总截止后，现有结构已能支持较从容的探索。

后续若试玩仍觉得等待太多，可考虑“阅读时冻结模拟、确认行动时推进”：阅读与现实体验时间分离，调查、等待和行驶才推进场景时间。这会改变两岗位并行调查、报告交付与路线动画的结算，需要完整设计“先布置任务，再推进至下一事件”，不宜和取消总时限一次混改。

## 调整前的实现与改动范围（设计留档）

1. **服务器硬截止**：`server/core/implementation.ts` 的 `missionNow()` 把时间截断为 600000ms；scheduler 固定安排 600000ms deadline；成功判定额外要求 `arrivalMs <= 600000`。三处需同步修改。
2. **空调度队列**：去掉截止事件和医疗目标后，无活动任务/行动时事件候选可以为空，必须正常退出调度循环，不能继续读取 `next.due`。
3. **契约与旧记录**：公共投影、SSE、内部启动事件把 `missionDeadlineMs` 写成常量 600000。新版本应使用明确的无限策略及可空时限，不使用 `Infinity` 或极大数字伪装；旧封存记录保留原规则版本和含义。
4. **所有时间入口**：`GameView`、`ContextModal`、`DecisionModal`、简报、双语剧情和结局文本一起调整。只去掉顶部数字不能改变游戏规则。
5. **医疗目标**：当前八分钟仅将 `stable` 改为 `target_missed` 并提示优先转送，不会减少人数或强制失败。自由探索版可移除这个现实时间触发器，避免保留隐性催促。
6. **长会话成本**：现有 `clock.sample` 每秒持久化；没有截止后会不断增长。需要限制时钟采样的存储、支持客户端重新同步，同时保留决策和证据日志，不能为清理容量暗中让玩家失败。
7. **保存与挂起**：浏览器断开目前不会暂停；服务重启会把活动局封为技术中断。若产品要支持隔天回来继续玩，需新增可恢复挂起/续玩机制；云端活跃会话限制也要配套修改。
8. **评价边界**：评分快照可新增到结局与导出；现有行为分析仍按冻结证据、序列与决策上下文工作，不让 AI 自行推测玩家时间或资源余额。

建议分两次独立 Git 迭代：先实现无限时长、正计时、医疗文案及必要的长会话保护；验证后再做数值评分与效率奖励。所有新局固定其规则版本，旧历史复盘不重算。

## 验收重点

- 超过原 600 秒后仍可调查、做决定、继续行驶并正常成功抵达。
- 长时间只阅读不会消耗额度、移除线索或自动结束任务。
- 没有待处理行动时调度正常；两岗位并行、WAIT、离场取消与原有成本语义保持正确。
- 600 秒后的 SSE 位置仍更新，Unity 车辆照常移动；刷新不重置累计用时。
- 中文、英文、弹窗、简报和复盘均无倒计时或超时失败残留。
- 新无限局与旧限时历史都能正确读取和导出。
- 较长会话或断线不会无限积累无用时钟事件；挂起与结束有清晰区别。

本轮已实施的范围以[无限时长试玩版](../implementation/无限时长试玩版.md)为准；效率评分和后续功能不能视作已上线。
